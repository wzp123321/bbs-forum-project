# Spec Delta

## Purpose

定义用户档案的可编辑字段与校验规则，以及头像、昵称在所有展示位的一致口径——保证同一个用户在列表、详情、评论、通知里的呈现是同一张脸。

## ADDED Requirements

### Requirement: 用户档案字段

用户档案 SHALL 包含昵称、头像、个性签名三项展示字段。

- 昵称 `nickname`：长度 2–20 个字符，允许中文、字母、数字、下划线，不要求全站唯一。
- 头像 `avatar`：仅存 URL（指向本站附件服务），不存二进制。
- 个性签名 `signature`：长度 0–100 个字符，可为空。
- 注册时昵称默认取用户填写的用户名；升级前已存在的用户，昵称回填为原用户名。
- 昵称 MUST NOT 为空：提交空值或全空白时按用户名校验失败处理。

#### Scenario: 新注册用户自动获得昵称

- **WHEN** 用户以用户名 `alice` 注册成功
- **THEN** 其档案昵称为 `alice`

#### Scenario: 存量用户昵称回填

- **WHEN** 升级脚本执行完毕
- **THEN** 所有既有用户的昵称等于其用户名，无一为空

### Requirement: 档案编辑

登录用户 SHALL 能修改自己的昵称、头像、个性签名、性别、邮箱、手机号。

- 只能修改本人档案，请求其他用户 ID 时 MUST 被拒绝。
- 昵称、签名提交前 MUST 经过敏感词过滤，命中则拒绝并提示。
- 头像 MUST 指向本站上传接口返回的地址；外部 URL 拒绝写入。
- 修改邮箱或手机号时 MUST 校验其未被其他账号占用。
- 档案接口的响应 MUST NOT 包含密码字段（含哈希）。

#### Scenario: 修改昵称与签名

- **WHEN** 用户把昵称改为「阿枢的三分地」、签名改为「写代码，也写字」
- **THEN** 保存成功，随后该用户在帖子列表中显示新昵称

#### Scenario: 昵称超长被拒

- **WHEN** 用户提交 21 个字符的昵称
- **THEN** 接口返回参数错误，档案不变

#### Scenario: 昵称含敏感词被拒

- **WHEN** 用户提交含敏感词的昵称
- **THEN** 接口拒绝保存并提示包含敏感词

#### Scenario: 不能改他人档案

- **WHEN** 用户 A 提交带用户 B 标识的档案修改请求
- **THEN** 接口拒绝，用户 B 档案不变

#### Scenario: 响应不含密码

- **WHEN** 客户端请求任一用户信息接口
- **THEN** 响应体中没有密码或密码哈希字段

### Requirement: 展示一致性

凡展示用户身份的位置 SHALL 使用统一口径：昵称优先，头像缺失有占位。

- 展示优先级为 昵称 → 用户名，昵称为空时 MUST 回退用户名，不得显示空白。
- 头像为空时 MUST 展示昵称首字符占位，不得出现裂图。
- 帖子列表、帖子详情、评论列表、通知列表、用户主页 MUST 使用同一口径。
- 服务端返回的作者信息 MUST 包含 `userId`、`nickname`、`avatar`，前端不得为每条记录单独请求用户信息。

#### Scenario: 昵称为空回退

- **WHEN** 某用户昵称为空（历史数据异常）
- **THEN** 列表与其帖子详情均显示其用户名

#### Scenario: 无头像显示占位

- **WHEN** 用户未设置头像
- **THEN** 其帖子卡片头像位置显示昵称首字符圆形占位

#### Scenario: 列表不产生 N+1 请求

- **WHEN** 打开帖子列表（20 条，涉及 8 个作者）
- **THEN** 前端只发出一次列表请求，作者头像昵称已在该响应内
